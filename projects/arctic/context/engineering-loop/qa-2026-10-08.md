## Remediation verification — local run (2026-10-08)

The Vercel production error groups confirmed the API 500 root cause: PostgreSQL's session-mode pool rejected connections with `EMAXCONNSESSION`, capped at 15 sessions. The live dashboard and client, booking, branch, technician, and inventory requests were affected. The approved-request conversion failure was observed in production as HTTP 409, but retained logs did not identify its exact Prisma error code.

The following fixes are implemented in the working tree and have not yet been deployed:

- Vercel/serverless Prisma clients now use one connection per instance. Prisma pool and transaction timeouts map to HTTP 503 with `Retry-After`; true transaction write conflicts (`P2034`) remain HTTP 409. Server logs include Prisma error codes.
- Service-request conversion waits longer for its row lock and transaction, and the integration test sends two simultaneous conversion requests, requiring one 201 and one idempotent 200 for the same single work order.
- Service-request status and estimate mutations update the open detail and inbox immediately. Conversion errors no longer show the template retry action; it is reserved for template-loading errors.
- The new-client booking form distinguishes `Client address` from the technician's `Service address`. Global Ctrl+K search focuses its query field. Empty low-stock inventory now distinguishes a branch with no catalog from a stocked branch with no low items.
- The branch-location migration preserves IDs and validates the four exact legacy branch rows before renaming. It no-ops when a local/demo database has no `Arctic Aircon` organization and fails before changing data if the production target is ambiguous or incomplete.

## Production dashboard receipt normalization — 2026-10-08

The dashboard failure remaining after the first remediation deploy was `/api/v1/overview` returning 500 because the monthly receipt aggregate called `.toNumber()` on a value that production supplied as a JavaScript number. The raw-query result type had claimed every runtime would return `Prisma.Decimal`.

The controller now accepts `Prisma.Decimal | number` for this aggregate and converts it with `Number(value ?? 0)` at the response boundary. Summary and invoice arithmetic remain Decimal-based; this change only normalizes the existing numeric chart field.
